# Spec: opening another profile works in the packaged desktop

Status: implemented
Lane: `pillar:platform`
Relates to: `src-tauri/build.rs`, `src-tauri/capabilities/default.json`, `src-tauri/src/lib.rs`, the
Profiles page (`profiles.html`) and the sidebar profile switcher (`_sidebar.html`).

## 1. Problem

Founder report, 2026-10-02: creating a second profile worked, but opening it failed with the toast
"Could not open that profile: Command open_profile not allowed by ACL". The Profiles page's **Open**
button and the sidebar switcher both call the Tauri command `open_profile`, so neither could ever
switch profiles in the packaged app.

The window shows the backend over `http://127.0.0.1:<port>`. To Tauri that is a **remote** origin, and
for a remote origin Tauri refuses every command that no capability explicitly grants (tauri 2.11,
`webview/mod.rs`: a request from a non-local origin is rejected unless `invoke.acl` resolved). An app
command can only be granted once the app declares it in an **app manifest**, because that is what
generates its `allow-<command>` permission. Neither half existed: `build.rs` was a bare
`tauri_build::build()`, and `capabilities/default.json` listed only plugin permissions. The command's
own description in that file even claimed it was "scoped to that local origin below", which was never
true.

It never reproduced anywhere except the packaged app: a browser has no Tauri IPC, `cargo tauri dev`
against a local page is a local origin, and the Python tests cannot see it. That is how it shipped, and
it also means `open_profile`'s body had never once run in production, so this spec also covers
checking that the rest of the chain works once the ACL lets it through.

## 2. Requirements

- R1. `open_profile` is callable from the local backend's origin (`http://127.0.0.1:*/**`,
  `http://localhost:*/**`), on every page of it including `/`.
- R2. It stays unreachable from any other origin: the grant must not widen the capability's `remote.urls`.
- R3. Once allowed, it actually runs: start the chosen profile's backend, read its `PORT=` line, wait
  for it to answer HTTP, record which profile is showing, and re-point the window.
- R4. A future `#[tauri::command]` cannot repeat this silently: the rule is written down where a
  developer adding one will see it.

## 3. Fix

- `build.rs` now calls `tauri_build::try_build` with `AppManifest::commands(&["open_profile"])`,
  which generates the `allow-open-profile` / `deny-open-profile` permissions
  (`src-tauri/permissions/autogenerated/open_profile.toml`, committed so a reviewer sees exactly what is
  granted; it is regenerated identically on every build).
- `capabilities/default.json` lists `allow-open-profile`. Its `remote.urls` are unchanged.
- `open_profile`, `spawn_backend` and `show_on` are now generic over `R: Runtime` instead of the concrete
  `Wry`, which is what lets Tauri's mock runtime host the real handler in a test. Production
  monomorphizes to `Wry`, so behavior is unchanged. `generate_context!()` moved into one `app_context()`
  helper because it embeds Info.plist under a fixed symbol and cannot be expanded twice in one crate.
- The profile id is passed to the sidecar as the `ANTHILL_PROFILE` environment variable and
  `anthill/profiles.py` only uses it as a lookup key into the registry (an unknown id falls back to the
  default profile), so enabling the command does not open a path-traversal or injection route.

## 4. Acceptance criteria

- From `http://127.0.0.1:<port>/`, `.../profiles` and `http://localhost:<port>/...`, `open_profile` is
  not rejected by the ACL.
- From `https://example.com/...` or a LAN address, it is rejected by the ACL.
- With a stand-in backend, `open_profile` returns `Ok`, and the shell records the requested profile as
  the one showing.
- Removing the `allow-open-profile` grant makes the first and third checks fail while the second still
  passes (the tests are sensitive to the fix, not vacuous).

## 5. Verification

`cargo test --lib` in `src-tauri/` (5 tests: the 2 existing port-parser tests plus 3 new `acl_tests`)
drives the real embedded capabilities through Tauri's mock runtime with a request that carries the
origin the shipped window uses:

- `open_profile_is_allowed_from_the_local_backend_origin` (root, `/profiles`, and a `localhost` origin);
- `open_profile_is_still_refused_to_any_other_origin`;
- `open_profile_starts_the_chosen_profiles_backend_once_allowed`, which installs a stand-in
  `anthill-server` (prints `PORT=<n>`, then serves HTTP) where Tauri resolves it, runs the real
  handler, and asserts `Ok` plus the recorded profile.

The first run on the unfixed code reproduced the founder's error verbatim (debug-build wording:
`open_profile not allowed. Plugin not found`). Removing only the grant afterwards made exactly the
allowed-origin and end-to-end tests fail. The tests restore the original sidecar file and kill the
backend they start; no process is left behind.

**Not covered here:** a real packaged build driving the real PyInstaller sidecar in a real window. The
fix only reaches an installed app through a release build, so that check belongs on the first build that
contains it. CI does not run Rust tests today (it only runs `tauri build`).

## 6. Non-goals

- Changing the capability's remote origins, or granting any other command.
- Adding a CI job for the Rust tests (a pipeline change, left for a separate decision).
